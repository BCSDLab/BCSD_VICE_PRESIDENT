# 장부 검수 절차

검수는 명시된 대상 기간·원본·산출물에 한정한다. 보고서는 **확정 오류 / 정상 확인 / 추가 확인 필요 / 검증 불가**를 나누고 각 판단에 파일·시트·페이지·행·거래 순번과 대조 근거를 붙인다. 확인되지 않은 사실을 추정해 정상 처리하지 않으며, 운영 원본과 검수 대상 파일은 수정하지 않는다.

## 1. 범위·증거·신뢰 경계

- `README.md`와 실제 코드, 대상 기간, 은행 파일, 관리·납부 시트, 제출 XLSX/HWPX, 영수증 원본, 템플릿, 해당 기간의 실제 이전 제출 완성본을 확인한다. 이전 제출본이 공식 최신 양식인지는 공지/현재 템플릿과 별도로 확인한다.
- 실제 API/인증 경로와 현재 권한을 확인하고 필요한 범위만 읽는다. 서비스 계정 접근 가능성을 운영 원본 변경 허가로 간주하지 않는다. 인증값을 터미널·보고서에 노출하지 않는다.
- 각 입력의 범위/완전성을 확인한다. 은행 거래 전건·모든 원본 시트·PDF 전체 페이지·각 지출에 연결된 모든 링크와 이미지를 기준량으로 삼고, 파서가 만든 결과 수량을 독립적인 원본 수량 대조 없이 전수라고 하지 않는다.
- 원본 은행 파일 이름과 시트 문자열은 Unicode NFC/NFD 차이로 눈에 보이는 이름이 같아도 일치하지 않을 수 있다. 비교 전에 이름을 정규화하고 실제 시트 목록을 기록한다.
- 회비 면제·탈퇴·Security 제외, 이름이 변형된 동일인 판단, 사유에 따른 적용은 [사유 자동 판단](../../bcsd-fee-management/references/workflow.md#사유-자동-판단)에만 따른다. 학번과 현재 회원/트랙 정보 등 같은 사람이라는 근거를 요구한다. 이름이 없다는 사실만으로 미납을 단정하지 않는다.
- 조사 결과는 원본과 산출물을 고치지 않고 보고한다. 제안된 셀 수정은 관리 문서 업데이트로, 파일 편집·재생성은 장부 작성으로 이관한다. DM은 보내지 않는다.

## 2. 거래와 회비의 전수 대조

### 은행 원본 파싱 검증

현재 `ledger_filler/filler.py::parse_transaction_file`은 `openpyxl.load_workbook(..., data_only=True)`의 **active sheet 하나**를 읽고, 2행부터 지정 열의 거래를 추출한다. 따라서 검수 대상 원본의 모든 시트·숨김 여부·시트별 거래/요약 구성을 먼저 열어 확인하고, 그 parser 결과만으로 은행 전체 내역이라고 단정하지 않는다. 본문 거래가 다른 시트에 있으면 그 범위를 별도로 추출해 대조한다.

- 파일의 worksheet dimension이 잘못 `A1:A1`로 저장된 경우 `read_only=True` 순회는 실제 거래를 숨길 수 있다. 현재 parser는 기본 일반 모드이며 `read_only`를 쓰지 않는다. 다른 도구/별도 검증 코드에서 read-only 사용 여부를 확인하고, dimension이 의심스러우면 일반 모드로 재검토하거나 `reset_dimensions()`를 적용한 읽기 전용 사본/검증 흐름으로 범위를 확인한다. 원본 파일 자체는 변경하지 않는다.
- 은행 원본 건수·입금합계·출금합계와 parser 추출 건수를 각각 기록하고 거래 열/끝행까지 독립 확인한다. 정상적인 0건과 파서가 dimension/시트 때문에 거래를 놓친 경우를 구분한다.
- 거래 원본과 관리 문서 및 제출 장부는 `(거래일시, 부호 있는 금액, 내용/이름, 잔액)`으로 비교하며 중복 발생 건수까지 맞춘다. 합계 일치만으로 완전성을 승인하지 않는다. 날짜는 시각 정밀도 차이를 숨기지 않고 원본 표기 수준으로 대조한다.
- 각 거래 뒤 잔액 연결을 검사한다. 시작잔액은 첫 거래 후 잔액에서 첫 거래의 부호 있는 금액을 뺀 값, 종료 잔액은 기간 마지막 거래 후 잔액이다. 기간 말 이후 거래 유무와 동일 시각 거래 순서는 은행 원본으로 확인한다. 상단 현재 잔액을 거래 당시 잔액으로 대체하지 않는다.
- 관리 문서의 해당 월 행 수, 원거래 중복 수, 소계·연간 합계 수식과 계산 결과를 확인한다. 행 번호나 소계 위치는 현재 시트에서 다시 찾는다.
- 관리 문서와 납부 문서는 각각 독립된 파일/시트로 조회한다. 이름·트랙·학번을 구분하고 변형된 이름을 동일인으로 볼 근거를 남긴다. 날짜/금액만 보고 회비·환불을 분류하지 않는다.
- Security는 미납 명단·미납 금액·안내 대상에서만 기본 제외한다. 전체 은행 거래 대조에서는 제외하지 않는다. 탈퇴·졸업·휴학·면제의 판정은 위 사유 자동 판단 링크를 따른다.

## 3. 영수증·수수료·환불·중복

각 출금에 연결된 링크를 원본 관리 문서에서 확인한다. Google Sheets `textFormatRuns[].format.link.uri`, 셀 hyperlink, `HYPERLINK` 수식을 확인하며 첫 링크만 얻는 XLSX 파서 결과가 모든 링크를 포함한다고 가정하지 않는다. 링크 수와 다운로드한 원본 파일 수, 생성 산출물 이미지 수를 교차 대조한다.

- 모든 실제 영수증 이미지를 원본 해상도로 열어 날짜, merchant/수취인, 총액, 통화, 품목/정산 내용을 읽는다. 채팅 축소 미리보기나 OCR/텍스트 추출만으로 판정하지 않는다. 필요한 세부가 잘렸거나 해상도가 부족하면 검증 불가/추가 확인으로 둔다.
- 영수증 폴더·파일명 날짜는 단서일 뿐 영수증 발생일로 단정하지 않는다. 영수증 날짜와 은행 이체일이 다를 수 있으므로 날짜, 상대방, 금액, 실제 문서를 함께 확인한다.
- 여러 영수증/개인정산이 한 번의 이체로 합산됐으면 각 문서의 부담액과 합계를 따로 대조한다. 개인 정산액과 사업자 영수증의 총액 차이를 설명 없이 오류 또는 정상으로 분류하지 않는다.
- 취소/환불은 원거래와 별도 은행 거래로 찾아 상호 연결한다. 동일 금액의 입출금은 환불 증거가 아니다. 중복 첨부는 같은 문서가 두 번 들어간 상태, 중복 계상은 거래/금액이 장부에 두 번 반영된 상태로 구별한다.
- 각 출금의 증빙 존재 여부, 매칭의 날짜·merchant/수취인·총액 근거, 누락/미매칭 페이지, 한 페이지의 중복 사용 여부를 기록한다. 증빙 없는 출금은 완전성에 영향을 주는 미해결 건으로 남긴다.
- 이체확인증 PDF는 모든 페이지를 세고 실제 페이지 이미지와 파서 결과를 대조한다. `ledger/hwp/transfer_proof.py`는 텍스트에서 거래일시, 입금금액, 수수료(없으면 0)를 읽어 `total=입금금액+수수료`로 만들고, 1차로 날짜+총액을 매칭한 뒤 남은 건에 날짜 없이 총액만 일치하는 fallback을 적용한다. 동일 금액/복수 후보, 날짜 불일치, 미매칭, 파싱 실패, 중복 사용 가능성을 실제 페이지의 수취인·날짜·총액과 대조한다. fallback 결과는 자동 확정하지 않는다.
- 현재 `main.py`의 수수료 플래그는 HWP 생성기에 전달되며 `ledger/hwp/hwp_generator_xml.py`와 `hwp_generator.py`는 boolean이 참이면 문구를 `(이체 수수료 500원)`으로 고정한다. 반면 transfer parser는 PDF에서 실제 금액을 추출해 금액 합산/매칭하고, `main.py`는 매칭 결과에 따라 수수료 boolean을 보정한다. 따라서 실제 수수료가 0원 또는 500원이 아닌 금액이면 boolean/제목만으로 금액이 정확하다고 하지 말고 실제 PDF와 생성 문구를 대조해 한계를 보고한다. 현재 README가 실제 수수료로 표기가 자동 보정된다고 해도 실제 generator의 500원 고정 구현이 우선이다.
- OCR/파서 금액과 페이지 이미지의 실제 내용이 다르면 이미지와 원본 거래를 우선 근거로 삼되, 코드 동작 차이도 기록한다. 이미지의 보이는 영역이 잘렸거나 일부 페이지가 없으면 검증 불가다.

## 4. 제출본 양식과 실제 산출 검증

템플릿만이 아니라 해당 제출 기간의 **실제 이전 완성본**을 비교 기준으로 확보한다. 입력된 제목·기간·차수·잔액, 표 데이터/행수 증가와 기본값 생략은 서식 차이와 나눠 본다.

- XLSX는 스타일, 글꼴, 채우기, 테두리, 정렬, 숫자 형식, 행 높이, 열 너비, 병합, 인쇄 영역/방향, 페이지 분할을 비교한다. 값 입력으로 사용된 셀/행의 증가는 그 자체로 서식 변경이 아니다. XML에서 기본값 생략, 스타일 ID 재번호, openpyxl `StyleProxy` 비교 불일치는 실제 시각/구조 차이인지 확인하기 전에는 오류로 세지 않는다.
- HWPX는 ZIP 무결성, `Contents/section*.xml`, `Contents/content.hpf` manifest, 이미지 바이너리 참조, 페이지/장부 순번, 표지 및 텍스트를 점검한다. 스타일 ID 숫자만 비교하지 말고 의미/렌더링을 비교한다. 잔존 이미지·삭제 문구·Preview (`Preview/PrvText.txt`, `Preview/PrvImage.png`)의 불일치도 확인한다.
- 관리/납부/제출 간 거래 순번과 금액, 숫자형 셀, 잔액, 링크/이미지 배열을 대조한다. 표지 입력, 기존 수동 캡처, 증빙 전부가 출력에 실제 포함되는지 확인한다. 표지 또는 설명이 템플릿과 다르다고 곧바로 오류로 단정하지 말고 실제 제출본/요청 기준과 대조한다.
- HWPX를 PDF/이미지로 실제 렌더링해 표지, 다중 이미지, 추가 확인증, 첫·마지막 거래, 페이지 넘김, 잘림/누락을 확인한다. 한컴 한글이 아닌 LibreOffice/H2Orestart 등으로 변환했다면 환경을 명시하고 변환기 경고의 영향을 확인한다. 텍스트/XML 검토만으로 실제 출력 검증이라고 하지 않는다.
- 작업 중 원본·산출물을 수정하거나 임시 생성 파일로 기존 결과를 교체하지 않는다. 검수 도구가 파일을 만들면 별도 격리 경로에 두고, 재현성/검수에 필요한 범위만 유지한다.

## 5. 결과 형식과 기준

결과는 표 또는 간결한 목록으로 아래 네 분류를 분리한다.

| 분류 | 기준 |
|---|---|
| 확정 오류 | 원본과 직접 대조 가능한 누락/중복/금액·잔액 불일치, 실제 영수증·출력에서 확인한 잘못된 증빙/서식 등. 원본 위치와 값 명시 |
| 정상 확인 | 명시된 범위 내 원본 전건/수량과 대조했고 독립 증거가 일치함. 확인 범위 밖은 정상에 포함하지 않음 |
| 추가 확인 필요 | 복수 후보, 설명되지 않은 차이, 휴리스틱 매칭, 정보 부족 등 사용자의 판단/추가 자료가 필요한 상태 |
| 검증 불가 | 원본 접근 불가, 누락된 페이지/시트, 낮은 해상도, 렌더링 불가 등 해당 검사를 수행할 수 없음 |

각 항목에 파일·시트·행/거래 순번 또는 PDF/HWPX 페이지 번호, 비교 대상, 수량·금액과 근거를 기재한다. 확인한 파일과 시트/페이지 범위 및 제외 범위를 함께 밝혀 “전수”의 의미를 과장하지 않는다. 오류 수정을 수행하지 말고 장부 작성 또는 관리 문서 업데이트로 이관한다.
